# Historical evidence conflict investigation

Saved decision history can show the disagreeing native facts for project edits/tasks, worker checks, and application activation/recovery. The existing owner-scoped history read supplies this projection; opening it never invokes a model, test, native refresh, approval, transfer, installation, or job replay.

Each unresolved investigation identifies its evidence family and a SHA-256 reference for the complete collected history inputs, before the display limits. Those inputs include related owner decisions and their observations, including later Undo and pending observations. Unrelated families and other owners do not change this reference. Independent store reads are sequential; this reference identifies collected inputs, not an atomic snapshot or live state.

The view shows at most eight distinct fact variants and four review/event witnesses per variant. Counts and omitted entries remain explicit. The first two variants provide an actual incompatible pair. A legitimate application failure followed by rollback is not itself a conflict. Timestamps do not select an authoritative winner, and original failed checks and restoration history remain visible.

Suggested next steps are fixed guidance: inspect original project results, inspect original worker receipts without replaying uncertain work, or inspect application activation/recovery evidence. New actions use the normal separate review and authorization flow. The investigation grants no authority and cannot resolve, erase, rewrite, or expire existing observations.

Malformed investigation metadata displays an unavailable warning while preserving the original valid history. Existing history without an investigation remains readable. Source and browser workflow tests do not establish new model-reviewer acceptance, current machine health, or completion of the broader evidence lifecycle roadmap.
