# Explicit initialization recovery qualification

The first installed initialization attempt refused after creating its authenticated transaction key and before publishing a migration journal or independent-process baseline. Its initial-state guard was incorrectly invoked again during constructor journal inspection and rejected the transaction directory it had just created. The original failure, source closure and contract are retained. A subsequent normal-profile read-only inspection reported original R5 runtime and two workers; this is observation evidence, not a claim that migration completed.

The correction places the initial-plan guard at the explicit store boundary under the outer lock before initial directory/key creation. Ordinary authority checks remain phase-aware. A separately selected `resume-initialization` operation authenticates the existing protected key and exact plan scope, requires the transaction directory to contain only `key.dpapi`, and verifies original R5 bytes and immutable authority. It never rewrites that key. Unknown, partial or later-phase evidence refuses recovery without deletion.

Only after authenticating that exact key-only state may the guard omit its own transaction name from the initial-preflight verification view. Foreign transaction entries, changed original process identities, changed task/session/authentication state and changed original payloads remain refusal conditions. The provider rechecks the key-only state and exact original plan under the outer lock, then publishes the independent-process baseline before the first task action. Ordinary resume continues to refuse a missing baseline; this is an explicit pre-task initialization recovery, not retrospective reconstruction after migration.

The current combined suite passed **114 tests in 23.54 seconds**. Independent recovery/preservation/boundary testing passed **26 tests**. These include actual generated-root DPAPI/file IO, injected authority/task observations and synthetic Scheduler launcher checks.
