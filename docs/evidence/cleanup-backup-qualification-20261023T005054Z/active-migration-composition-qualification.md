# Generated native migration composition qualification

This component composes the unchanged migration core with the qualified Windows store and mutex owner, an actual unique generated Task Scheduler task, and identity-bound native processes. It remains fixture-only: no production task/root name or live activation entry exists. Production activation is false.

Process topology is explicit. Task Scheduler launches a generated PowerShell 7 owner driver. That process loads a verified local copy of the signed R5 QuietHost assembly and invokes its previously qualified internal Run primitive. The contained immediate child is Windows PowerShell running a generated supervisor script. Generated application/controller/communication descendants escape containment as intended. There is no separately launched QuietHost executable process in this topology. This does not qualify the signed production supervisor script or a production task action; the earlier signed QuietHost proof remains separate evidence.

The provider reuses the existing task ownership/configuration/identity functions through pinned AST extraction. It compares normalized full task XML (normalizing only the direct Enabled setting), exact task name/action/arguments/principal, immutable generated asset hashes, and the signed assembly hash before operations. Setup binds actual generated task XML and canonical identity observations into the synthetic plan before first store key creation. Original R5 receipt and synthetic authorization remain byte-for-byte unchanged throughout each migration.

The core holds the same store-owned outer mutex object across callbacks. Runtime mutexes are acquired only for the quiescent filesystem interval and are checked released immediately before restore and Start. The provider retains exact native process handles, validates creation/image/owner/session and exact parsed commands, stops only the owning driver, and waits for the contained supervisor. A missing driver does not establish child exit: the original child is checked independently. Independent descendants are verified alive by native identity after completion. Normal migration does not terminate those descendants; only final generated-fixture cleanup does.

Start has an authenticated transaction-bound generation intent, a flushed launch request, a create-only per-driver generation record, and an authenticated observed pair receipt. Recovery adopts only the exact pending generation. Existing completed-start evidence with an absent/different pair refuses rather than issuing another Start. A pending start with no demonstrable pair is preserved as ambiguous rather than assuming the scheduler call never happened. Task action/XML is never modified to add generations. Completed-state acceptance validates exact start intent/receipt schemas and generation bindings in addition to current task, pair, signed runtime and verified backup state; filesystem journal phase alone is insufficient.

Qualification is recorded by source revision, without combining different revisions into an all-suite pass claim. Native cases across the recorded runs cover enabled/running, enabled/stopped and disabled/stopped baselines; actual fresh-process os._exit interruptions at nine phase/operation boundaries; lost Start completion without a duplicate driver; incomplete Start publication and stale generations; and an already-recorded start whose pair is gone. Task XML/principal/action mismatch and extra-command-argument checks use isolated API observation injection, explicitly distinct from modifying actual Scheduler configuration. Role/token/parent refusal checks operate against real generated processes. CloseHandle failure accounting is API-injected; remaining handle closes are attempted and unresolved ownership is retained. Disabled/running setup refuses before task creation.

The first frozen candidate exposed a generated-supervisor startup observation race: MainModule could briefly report no image or ntdll.dll immediately after launching a stand-in. Cleanup correctly refused the ambiguous records. Initial main group A recorded six passes and one cleanup failure, group B six passes, and the independent selection three passes and one cleanup failure. Those failures and original records remain preserved. Separate recovery used exact original creation/owner/session plus expected executable, full generated command, role/token/parent and retained native handles; it did not overwrite the bad records or rely on PID alone.

The corrected fixture publishes create-only provisional launch identity before waiting up to eight seconds for the expected executable image and stable creation time, then publishes final readiness identity. Normal acceptance still requires final records. Cleanup accepts provisional records only after full native identity and exact command verification. A forced readiness-timeout test proves a live child is still discoverable and its retained handle signals exit after cleanup. The independent corrected two-case run passed both this timeout case and the prior ownership-negative case in 72.96 seconds. The provider callback class AST was unchanged by this fixture producer/cleanup correction.

A final failure-accounting-only revision records failure of a temporary probe CloseHandle rather than silently treating that close as successful. Its exact diff leaves the native success path unchanged. Both primary and independent isolated injected tests passed; the native run hashes and the final accounting revision are recorded separately.

Each successful or refused native case preserves original receipt/auth hashes, raw child stdout/stderr/exit evidence and generated cleanup receipts. Cleanup validates per-PID creation/image/owner/session/exact command before obtaining retained native handles; attempts each role independently; and records failure rather than claiming release after an uncertain CloseHandle. Evidence roots are retained. Stand-ins have bounded ten-minute self-exit and the task has a twelve-minute execution limit; normal test teardown completes much earlier.

Limits: this is a cooperative same-session generated-root contract, not arbitrary same-user race protection or a cross-session exclusion guarantee. The existing store tests establish process-interruption behavior, not power-loss durability. No production enrollment, scheduler task, application/controller process, removable-drive pointer, or installed runtime is changed. No frozen core/store/lock component was modified. No production installation decision follows from this qualification alone.
