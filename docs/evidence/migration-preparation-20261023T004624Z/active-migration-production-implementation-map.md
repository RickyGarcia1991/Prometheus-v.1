# Minimal implementation map: production active R5 to R7 migration

This map identifies the remaining implementation needed to finish the requested active migration and restart. It is not a request to keep adding unrelated fixtures. The generated composition is a qualification input, not the production entry. No production mutation is authorized by this document and no generated-root guard should be weakened in place.

## Concrete deliverable

Implement one fixed-purpose production adapter (`active_host_migration_windows.py`) and its fixed-function native observation/task module (`ActiveHostMigration.Native.psm1`), plus a separately named normal-profile execution launcher. Bind these to the existing unchanged `active_host_migration_core.py`. The launcher accepts an exact reviewed transaction/plan artifact and operation enum; it does not accept arbitrary root/task/PID/command inputs. Preserve the inspect-only launcher and collector unchanged.

## Exact normal-profile execution gates

Run the execution worker in the real loaded owner profile, outside MSIX/virtualized redirection. Use the already qualified normal-profile launch/physical-handle techniques, but a new explicitly mutating worker/launcher; do not repurpose an inspect-only command. Freshly prove un-packaged context, current SID, unique matching loaded profile and final handle paths for every read target. This specifically avoids the previously observed file-level MSIX overlay behavior.

Before plan acceptance and again under outer locks: require existing authorization JSON and SHA sidecar to match, actual machine fingerprint to match authorization, actual task principal to resolve to current SID, original authenticated R5 enrollment receipt and exact digest to match, full task definition and enabled/running baseline to match, exact old runtime/signed closures, and no competing owned worker in an unsupported session. The supported contract is cooperative maintenance in one eligible interactive session; do not claim future/adversarial cross-session exclusion from a snapshot. Refuse unsupported context rather than creating authorization, repairing sidecars, minting an enrollment receipt or changing task ownership.

Retain read handles over immutable reviewed helpers/packages and bind their hashes in the transaction evidence. Verify target ancestry/final paths, owner/ACL and file identity before journal/backup/replacement writes. Use the original real profile DPAPI identity. Never reuse the generated-store or pointer-provider DPAPI domain as a production key namespace.

The live entry remains disabled until the production code, concrete transaction plan, current normal-profile observations, rollback material and independent review are all present. The existing user request supplies task scope; this technical gate does not invent another blanket permission cycle. Any separate environment/owner execution approval must be specific to the concrete reviewed action, not an open-ended arbitrary command.

## Rollback and completion gates

Before live HostAgent replacement, create and read back an exact signed R5 HostAgent backup with transaction ownership, and capture immutable original task XML/flags plus receipt/auth hashes. The forward core already preserves intent and ambiguity; it does not implement rollback phases. Do not reinterpret a completed/pending forward journal as a rollback receipt.

Provide a separate narrowly scoped rollback operation or a reviewed exact recovery procedure before attempting live replacement. It may restore only the transaction-owned exact R5 backup while current target is the transaction-proven R7 file (or verified unchanged R5). It must revalidate original authority/task ownership, disable the same task, stop only its exact retained current pair, hold runtime locks across replacement, verify old bytes, release runtime locks, then restore original enabled/running state. Preserve forward journal, backup and a separately authenticated rollback receipt. Refuse foreign bytes, changed task/auth, incomplete identity, missing key or uncertain backup; preserve evidence instead of automatic broad restoration.

After forward restart: prove the same task definition, original enabled state, exactly one owned actual pair when originally running (none when stopped), five expected R7 runtime hashes, unchanged original R5 receipt/auth and independent processes, and verified backup. Only then publish complete and qualify read-only completed-chain acceptance. Existing R5 consumers remain unchanged and must not be tricked into treating R5 receipt as R7 enrollment; add an explicit migration-aware consumer path where required.

## Tests that are necessary, and tests that need not be repeated

1. New production context/name/authority policies need targeted rejection tests: physical redirection/reparse/ACL, wrong SID/profile/host/sidecar, task action/principal/trigger/XML drift, unsupported session and actual current-pair ambiguity. Reuse the 61-case preflight evidence if its sources remain unchanged; run a fresh real read-only preflight because observations expire.
2. If extracting or changing lock ownership/store algorithms to share them with production, rerun their 49 native lock and 47 native store cases against that new engine. Merely importing unchanged primitives does not justify repeating those suites. New production name/root policies still require their own refusal tests without acquiring production locks during development.
3. Run new provider composition against isolated generated names/roots using its actual callback code: all supported baselines, lost Start completion, critical stop/replace/restore/start interruption and ambiguity paths, exact process/task refusal, rollback restoration and rollback refusal. Do not substitute the old fixture provider for tests of the production adapter's callbacks. Reuse unchanged core model tests and signed-package verification evidence rather than expanding alternative research/tool inventories.
4. After independent review, perform one controlled owner-profile live transaction with fresh observations, exact scope, retained rollback and bounded readback. Verify actual same-task restart and preservation of independent processes. This is the remaining live acceptance step; a fixture pass alone cannot complete it. If rollback is exercised, record it distinctly and do not report R7 installation until forward completion is proved.

No full backup, OS installation, Ubuntu activation or model download is prerequisite to implementing this production adapter. Those remain subsequent work after the requested companion migration/restart is actually complete.
