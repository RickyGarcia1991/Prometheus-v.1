# Missing controller activation boundary

Read-only design review. Existing Get-Package verifies trusted signature, payload hashes, signed provenance/version and monotonic protected floor. Sync-Controller stages cache and advances floor, but does not switch PROMETHEUS-SSD-STATUS.json controller_release. Existing isolated cache recovery deliberately excludes live pointer/process activation. Repair-Prometheus-Controller.ps1 is not a sufficient activation entry: its explicit release/launch route lacks the newer provenance/version and protected-floor gates.

The smallest addition is one bounded, recoverable transaction around the existing signed candidate/cache/floor checks and the single metadata pointer. It must preserve all unrelated metadata fields and original bytes, existing authorization, intentional-close semantics, and application/controller ownership.

Required invariants:

1. Identify the exact SSD and real unvirtualized profile; reject reparse/redirected paths. Acquire the same lifecycle/enrollment/eject exclusion used by the active supervisor, with a documented lock order. Recheck pause/eject state and exact current pointer before mutation. Refuse an active controller rather than replacing files under it.
2. Pin exact candidate and forward-recovery package manifests, signatures, provenance, complete payload sets and intended versions. Validate source and staged cache from the same immutable bytes; Sync-Controller currently rereads the staged manifest without verifying its signature, so merely validating its source earlier is insufficient against intervening replacement.
3. Save durable intent and exact old metadata before advancing the floor. Bind intent to host, volume, candidate/recovery hashes, previous pointer and transaction ID. A recovery record that grants write authority must be authenticated or independently rederive every allowed transition from pinned signed inputs; an editable JSON journal alone must not authorize arbitrary paths or rollback.
4. Ensure a verified forward-recovery package is available before monotonic floor advancement. After floor advancement never restore a lower-version pointer as successful rollback. Failure before advancement may retain old pointer; failure after it must finish the pinned candidate pointer or explicitly select qualified forward recovery at or above the durable floor.
5. Publish metadata via flushed same-directory staging and atomic replacement, with exact readback. Hold serialization until pointer, cache and floor agree. Recovery must recognize old/new exact pointer bytes, refuse unrelated edits, and be idempotent across every interrupted stage, including pointer-write success followed by journal failure.
6. Launch is a distinct final acceptance step, never implied by cache success. Verify exact executable path/identity and expected UI readiness; retain intentional close unless a manual launch was requested. Do not kill unrelated same-name processes or claim protected interface acceptance while locked.
7. Test generated faults before/after cache publication, durable floor advancement, metadata replacement and receipt publication; retry in a fresh process. Assert preserved unrelated fields, unchanged authorization/user data, no lower floor, no duplicate launch and refusal of changed source/pointer/journal. Cover both Windows PowerShell 5 and configured pwsh where supported.

The forward cache tests establish cache and floor recovery only. Physical SSD reinsertion, Windows reboot, and protected-interface acceptance remain separate and cannot be inferred from this transaction.
